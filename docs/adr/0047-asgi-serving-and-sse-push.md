# 0047 — The application is served over ASGI, and data versions are pushed over SSE

Gunicorn runs the ASGI application under uvicorn workers, and every change to a data-version source model is pushed to connected tabs over server-sent events; polling is the fallback for a tab whose stream is down, never the mechanism.

## Rules

- **Serve `config.asgi:application` under uvicorn everywhere**: production through `gunicorn -k uvicorn_worker.UvicornWorker` (unit and flags in `docs/server_setup.md`), the E2E harness in `scripts/ops/run_e2e.sh`, local development through the documented `python -m uvicorn` task. ASGI is what lets a worker hold many open streams, because a stream costs an event-loop task rather than a request slot. `CONN_MAX_AGE` stays 0: under ASGI every in-flight request gets its own thread-sensitive executor, so database connections bound concurrency rather than worker count, and raising it multiplies open Postgres connections by a number nothing has measured.
- **A stream yields from an `async` generator and asserts `response.is_async`.** `StreamingHttpResponse` decides `is_async` by whether `iter()` accepts what it was given, and a sync generator under ASGI is drained whole into a list before the first byte while holding a worker thread; status, content type and headers all look right, so the assertion is the only check that sees it. The trap is symmetric — an async generator over WSGI is drained the same way — which is why `manage.py runserver`, being WSGI, is never used to debug a stream.
- **Version bumps come from signals over a source-model registry, never from publish calls at write sites.** `DATA_VERSION_SOURCE_MODELS` in `apps/operations/push.py` mirrors `DATASET_VERSION_PROVIDERS`; add a dataset to one and you add it to the other, and `apps/operations/tests/test_push.py` fails when they disagree, because a dataset with a provider and no source models answers the poll correctly and silently never pushes. The publish runs once per transaction after commit with `robust=True`, so a Redis blip cannot abandon the commit's other callbacks; the module docstring carries the mechanism.
- **Queryset writes announce themselves through `JobQuerySet.untracked_update`**, the one Job UPDATE path, which calls `apps.core.data_events.notify_data_changed()` — the observer seam that lets `apps.job` announce a write without importing `apps.operations`. Announcing a write that moves no version is free; missing one is a permanently stale tab with no error anywhere.
- **The stream is django-eventstream, mounted as a plain view beside its polling sibling** (`apps/operations/events.py`, outside ninja and the OpenAPI schema, because an endless response is not an operation the generated client can call). It authenticates the cookie JWT directly, sets `Content-Encoding: identity` so `GZipMiddleware` leaves it alone, and its one event carries exactly the document the poll serves.
- **Cross-process fan-out is raw Redis pub/sub on a channel that includes the database name**: pub/sub is server-wide rather than scoped to a database index, and the instance's Redis serves both its live database and the copy the ADR 0064 window runs on.
- **No storage backend, so no event ids and no replay.** Every push carries the complete current document; a reconnecting tab fetches the versions once on `stream-open` and reconciles.
- **On the frontend the stream is primary and the poll is a disconnect-only fallback.** `frontend/src/api/data-versions-stream.ts` wraps the generated SSE client; the query observer defers only while the cached document is the one the stream last wrote and still reconciles an HTTP-originated write, because storage-free pub/sub drops a publication rather than queueing it.

## Do not

- **Put a server-side poll loop behind the SSE endpoint** — a stream fed by the server polling its own database is a poll with a longer connection, not push.
- **Add channels or channels-redis** — django-eventstream 5.x runs channels-free under ASGI.
- **Introduce Pushpin or another GRIP proxy** — a second network daemon on every host, for fan-out Redis pub/sub already does.
- **Enable eventstream's storage backend or Last-Event-ID replay** — every push carries the whole current document, so a replayed history tells a client nothing its next frame does not, and it buys a table and a retention question.
- **Call a publish helper from each write site instead of the signals** — a forgotten call site is a permanently stale tab with nothing logged anywhere.
- **Serve the stream through a ninja operation** — it lands in the OpenAPI schema, and the API-boundary gate then demands it be called through generated axios code that cannot consume an endless response.
